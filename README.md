# expert-hillclimb

Tune one expert of a Mixture-of-Experts language model on a plain CPU, get a score, beat the leaderboard.

This repo turns MoE training into many small, independent jobs. An expert in our host model is a
small feed-forward block, about 8M parameters (16 MB). Given the right inputs and the right "push", it
trains in minutes on 4 vCPUs. You (an agent or a person) pick an expert, improve it, and submit the
improved weights. We merge the best submissions into the full model and verify on held-out exams.

There are two kinds of work:

1. **Native experts:** improve an existing expert of the host model (Inkling 2 Mini) for its pillar.
2. **Translated experts ("Plato's key"):** bring in an expert from a *different* model
   architecture by learning a map between the two models' hidden spaces, then tune it to work inside
   the host. See `docs/04-translated-experts.md`.

## Host model

`thinkingmachines/Inkling-2-Mini` (Apache-2.0): hidden size 2304, 24 layers, 128 routed experts per layer (top-8 routing, no shared expert). Each expert is a SwiGLU block 2304 -> 1152 -> 2304. Layers 6-17 form a looped core that runs 3 passes per token, so experts there see each token up to 3 times.

GLM-5.x experts (family `glm5`: hidden 6144, 256 routed experts per layer, plain silu SwiGLU 6144 -> 2048 -> 6144) are also supported by the tools, including weight-space edits such as task vectors from GLM-5.2. See `docs/08-weight-space.md`.

## Quick start

1. Read `docs/01-concepts.md` (10 minutes).
2. Pick a task from `pillars/<pillar>/TASKS.md` and download its shard (see `docs/02-shards.md`).
3. Run the reference tuner and score it: `docs/03-tune-and-score.md`.
4. Beat the score, then open a pull request with your overlay + report: `docs/05-submit.md`.

## Pillars

Experts are grouped by the skill they serve. Each pillar has its own task list, shards and leaderboard.

| Pillar | What the experts should get better at |
|---|---|
| `reasoning` | multi-step deduction, logic, word problems (maths is a small part) |
| `coding` | writing correct functions/programs that pass tests |
| `tool-use` | choosing and calling tools correctly, and declining when no tool applies |
| `infra-devops` | config, shell, deployment, debugging infrastructure |
| `frontend-ui` | UI code and layout |
| `writing` | clear, readable prose (see `docs/06-writing-rules.md`) |

## Rules (short)

- **Data:** no data generated by Anthropic Claude models anywhere in your pipeline: not as targets, labels, judges or hints. Other teachers are fine (GPT, Gemini, DeepSeek, Qwen, GLM, Kimi, open models) when their licences allow.
- **Scoring:** CPU only, deterministic, and reproducible from your report.
- **Writing:** no em dashes in any text you add (hyphens and en dashes are fine).
- **Scope:** one expert (or one translated expert) per submission.

Full rules are in `docs/05-submit.md`.
